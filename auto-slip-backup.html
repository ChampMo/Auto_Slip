Auto Slip สำรองและกู้คืนข้อมูล

คู่มือสำรองและกู้คืนข้อมูล

สำหรับผู้ดูแลเซิร์ฟเวอร์ของระบบ Auto Slip — วิธีติดตั้งการสำรองอัตโนมัติ วิธีตรวจว่าไฟล์สำรองยังใช้ได้จริง และวิธีกู้คืนเมื่อข้อมูลเสียหาย

สำรองทันที
./scripts/backup.sh ปกติ cron ทำให้เองทุกวัน สั่งเองเมื่อจะแก้อะไรใหญ่ๆ
ตรวจไฟล์สำรอง
./scripts/restore.sh --check ไฟล์ ปลอดภัย ไม่แตะข้อมูลจริง ควรทำเดือนละครั้ง
กู้คืนจริง
./scripts/restore.sh ไฟล์ เขียนทับข้อมูลปัจจุบันทั้งหมด ต้องพิมพ์ยืนยัน

หัวข้อ 1ทำไมต้องสำรอง

ข้อมูลทั้งหมดอยู่ในฐานข้อมูลบนเซิร์ฟเวอร์เครื่องเดียว ถ้าเครื่องพัง หรือมีคนเผลอลบ ข้อมูลสามอย่างนี้จะหายไปพร้อมกัน

สิ่งที่หายผลที่ตามมา
ประวัติสลิปทั้งหมด ด่านกันสลิปซ้ำหายไปด้วย — สลิปเก่าทุกใบส่งเข้ามาซ้ำได้ทันทีโดยระบบไม่รู้ตัว
รายชื่อผู้อนุมัติ เหลือเฉพาะเจ้าของที่ตั้งไว้ในไฟล์ตั้งค่า คนอื่นต้องเพิ่มใหม่ทั้งหมด
บันทึกว่าใครกดอะไร ตรวจย้อนหลังไม่ได้อีกเลย

การสำรองไม่ได้ป้องกันเครื่องพัง แต่ทำให้กู้กลับมาได้ — ส่วนที่แพงคือข้อมูล ไม่ใช่เครื่อง

หัวข้อ 2ติดตั้งครั้งแรก

ทำครั้งเดียว หลังจากนั้นระบบจะสำรองให้เองทุกวัน

  1. อัปโหลดสคริปต์ขึ้นเซิร์ฟเวอร์

    อัปโฟลเดอร์ scripts/ ทั้งโฟลเดอร์ผ่าน FileZilla ไปวางที่ /root/Auto_Slip/scripts/

    ห้ามลืม

    ตั้งค่าโหมดถ่ายโอนเป็น Binary ก่อนอัป

    ใน FileZilla ไปที่ Transfer → Transfer type → Binary ถ้าใช้โหมด ASCII หรือ Auto ไฟล์อาจถูกแปลงท้ายบรรทัดเป็นแบบ Windows แล้วสคริปต์จะรันไม่ได้ ขึ้น error ว่า bad interpreter: /usr/bin/env bash^M

  2. เปิดสิทธิ์ให้รันได้

    ไฟล์ที่อัปผ่าน FileZilla จะยังรันไม่ได้ ต้องสั่งเปิดสิทธิ์เองหนึ่งครั้ง

    ทำครั้งเดียวหลังอัปครั้งแรก
    $ ssh root@139.59.224.209
$ cd ~/Auto_Slip
$ chmod +x scripts/*.sh

# เช็คว่าท้ายบรรทัดไม่ใช่แบบ Windows (ไม่ควรมี ^M ขึ้น)
$ head -1 scripts/backup.sh | cat -A
#!/usr/bin/env bash$            # ถูกต้อง — ลงท้ายด้วย $ เฉยๆ

    ถ้าเห็น ^M$ แทน ให้สั่ง sed -i 's/\r$//' scripts/*.sh แก้ทีเดียวจบ

  3. ลองสำรองด้วยมือหนึ่งครั้ง

    อย่าเพิ่งตั้งเวลาอัตโนมัติ จนกว่าจะเห็นว่าคำสั่งนี้ทำงานได้จริง

    ผลลัพธ์ที่ควรได้
    $ ./scripts/backup.sh
2026-08-06 15:30:01  กำลังสำรอง autoslip_db จากคอนเทนเนอร์ a1b2c3d4e5f6
2026-08-06 15:30:03  สำเร็จ: autoslip-20260806-153001.sql.gz (24K, 1847 รายการ)
2026-08-06 15:30:03  มีไฟล์สำรองทั้งหมด 1 ไฟล์ใน /var/backups/auto_slip

    ถ้าขึ้นข้อความที่ขึ้นต้นด้วย ล้มเหลว: ให้ดูหัวข้อ 6 ก่อนไปต่อ

  4. พิสูจน์ว่าไฟล์ที่ได้กู้คืนได้จริง

    ขั้นตอนนี้สำคัญที่สุดและคนมักข้าม — ไฟล์สำรองที่กู้คืนไม่ได้ ไม่นับว่าเป็นไฟล์สำรอง

    ไม่แตะฐานข้อมูลจริง
    $ ./scripts/restore.sh --check /var/backups/auto_slip/autoslip-20260806-153001.sql.gz
2026-08-06 15:31:10  ตรวจไฟล์ autoslip-20260806-153001.sql.gz โดยกู้ลงฐานข้อมูลชั่วคราว
2026-08-06 15:31:14  กู้คืนสำเร็จ ข้อมูลที่อยู่ในไฟล์:

  ตาราง         จำนวนแถว
  ──────────────  ────────
  transactions   1847
  used_qrs       1902
  approvers      4
  audit_logs     7215

2026-08-06 15:31:15  ไฟล์สำรองนี้ใช้งานได้ (ฐานข้อมูลจริงไม่ถูกแตะต้อง)

  5. ตั้งให้ทำเองทุกวัน

    ตั้งเวลาด้วย cron
    $ sudo crontab -e

# เพิ่มบรรทัดนี้ — สำรองทุกวันตี 3 พร้อมเก็บ log
0 3 * * * /root/Auto_Slip/scripts/backup.sh >> /var/log/autoslip-backup.log 2>&1

    เลือกตี 3 เพราะเป็นช่วงที่ไม่มีสลิปเข้า และห่างจากงานสร้างแท็บชีทตอน 22:59 (cron ใช้เวลาของเครื่อง ไม่เกี่ยวกับปฏิทินธุรกิจของระบบ)

เสร็จแล้ว

หลังจากนี้ไม่ต้องทำอะไรทุกวัน

ระบบจะสำรองเองทุกคืน เก็บย้อนหลัง 14 วัน และลบไฟล์เก่าให้เอง เหลือแค่งานตรวจเดือนละครั้งในหัวข้อ 3

หัวข้อ 3งานประจำที่ต้องทำ

ความถี่ทำอะไร
ทุกวัน ไม่ต้องทำอะไร cron จัดการให้
เดือนละครั้ง รัน restore.sh --check กับไฟล์ล่าสุด เพื่อยืนยันว่ายังกู้คืนได้จริง
นานๆ ครั้ง เปิดดู /var/log/autoslip-backup.log ว่ามีวันไหนล้มเหลวโดยไม่มีใครสังเกตหรือเปล่า
ก่อนแก้อะไรใหญ่ สั่ง ./scripts/backup.sh ด้วยมือก่อน เช่น ก่อนอัปเดตโค้ด หรือก่อนแก้ข้อมูลในฐานข้อมูลโดยตรง

ดูว่ามีไฟล์สำรองอะไรอยู่บ้าง

เรียงจากใหม่ไปเก่า
$ ls -lht /var/backups/auto_slip
-rw------- 1 root root  24K Aug  6 03:00 autoslip-20260806-030001.sql.gz
-rw------- 1 root root  24K Aug  5 03:00 autoslip-20260805-030001.sql.gz
-rw------- 1 root root  23K Aug  4 03:00 autoslip-20260804-030001.sql.gz

ถ้าไฟล์ล่าสุดเก่ากว่าเมื่อวาน แปลว่าการสำรองอัตโนมัติหยุดทำงาน ให้ดูหัวข้อ 6

หัวข้อ 4ตรวจว่าไฟล์สำรองใช้ได้

คำสั่ง --check จะสร้างฐานข้อมูลชั่วคราวขึ้นมา กู้ไฟล์ลงไป นับจำนวนแถวให้ดู แล้วลบฐานข้อมูลชั่วคราวทิ้ง ฐานข้อมูลจริงไม่ถูกแตะต้องเลย จึงรันได้ตลอดเวลาโดยไม่ต้องหยุดบอท

รันได้ตลอด ไม่ต้องหยุดบอท
$ cd ~/Auto_Slip
$ ./scripts/restore.sh --check /var/backups/auto_slip/autoslip-20260806-030001.sql.gz

อ่านผลยังไง

  • ขึ้น “ไฟล์สำรองนี้ใช้งานได้” — เรียบร้อย ไม่ต้องทำอะไรต่อ
  • ขึ้น “กู้คืนไม่สำเร็จ — ไฟล์สำรองนี้ใช้ไม่ได้” — ลองไฟล์ของวันก่อนหน้า ถ้าเสียหลายวันติดกันแปลว่าการสำรองมีปัญหามาสักพักแล้ว ให้รีบตรวจ log และแจ้งผู้พัฒนา
  • จำนวนแถวน้อยกว่าที่ควรมาก — เทียบกับ /today ในกลุ่ม Telegram ว่าจำนวนสลิปสมเหตุสมผลไหม

หัวข้อ 5กู้คืนข้อมูลจริง

อ่านก่อนทำ

คำสั่งนี้เขียนทับข้อมูลปัจจุบันทั้งหมด

สลิปที่เข้ามาหลังจากไฟล์สำรองถูกสร้าง จะหายไป ทำเฉพาะตอนข้อมูลเสียหายจริงเท่านั้น ถ้าแค่อยากดูข้อมูลเก่า ให้ใช้ --check ในหัวข้อ 4 แทน

  1. หยุดบอทก่อน

    กันไม่ให้มีสลิปใหม่เข้ามาระหว่างกู้คืน ซึ่งจะทำให้ข้อมูลปนกัน

    บอทหยุด ฐานข้อมูลยังทำงานอยู่
    $ cd ~/Auto_Slip
$ docker-compose stop bot

  2. เลือกไฟล์และสั่งกู้คืน

    ต้องพิมพ์ชื่อฐานข้อมูลยืนยัน
    $ ./scripts/restore.sh /var/backups/auto_slip/autoslip-20260806-030001.sql.gz

  ⚠  กำลังจะเขียนทับฐานข้อมูล "autoslip_db" ทั้งหมดด้วยไฟล์
     autoslip-20260806-030001.sql.gz

     ข้อมูลปัจจุบันทั้งหมดจะหายไป รวมถึงสลิปที่บันทึกหลังไฟล์นี้ถูกสร้าง
     ควรหยุดบอทก่อน:  docker compose stop bot

  พิมพ์ชื่อฐานข้อมูลเพื่อยืนยัน (autoslip_db): autoslip_db

    พิมพ์ไม่ตรงจะยกเลิกทันที ไม่มีอะไรเปลี่ยนแปลง

  3. ดูจำนวนแถวก่อนและหลัง

    สคริปต์จะแสดงจำนวนแถวทั้งก่อนและหลังกู้คืน ใช้ยืนยันว่าข้อมูลกลับมาจริงตามที่คาด

  4. เปิดบอทกลับ

    อย่าลืมขั้นตอนนี้
    $ docker-compose start bot
$ docker-compose logs -f bot   # ดูว่าบอทเริ่มได้ปกติ กด Ctrl+C เพื่อออก

    จากนั้นพิมพ์ /health ในกลุ่ม Telegram เพื่อยืนยันว่าระบบกลับมาทำงานครบ

หัวข้อ 6เมื่อมีปัญหา

ข้อความที่ขึ้นสาเหตุและวิธีแก้
หาคอนเทนเนอร์ฐานข้อมูลไม่เจอ ฐานข้อมูลไม่ได้ทำงานอยู่ ตรวจด้วย docker-compose ps แล้วเปิดด้วย docker-compose up -d db
Permission denied ไฟล์ยังไม่มีสิทธิ์รัน — เกิดทุกครั้งที่อัปไฟล์ใหม่ผ่าน FileZilla สั่ง chmod +x scripts/*.sh หรือรันด้วย bash scripts/backup.sh ไปก่อน
bad interpreter: /usr/bin/env bash^M
หรือ $'\r': command not found		 ไฟล์ถูกอัปมาแบบ Windows แก้ด้วย sed -i 's/\r$//' scripts/*.sh แล้วตั้งโหมด Binary ใน FileZilla ก่อนอัปครั้งถัดไป
ไฟล์เล็กผิดปกติ หรือ ไม่พบตาราง ... ในไฟล์สำรอง ดัมป์ไม่ครบ มักเกิดจากพื้นที่ดิสก์เต็มหรือฐานข้อมูลถูกปิดกลางคัน ตรวจพื้นที่ด้วย df -h — ไฟล์ที่ไม่ผ่านจะถูกลบทิ้ง ไม่ทับของเดิม
pg_dump ไม่สำเร็จ ชื่อผู้ใช้หรือชื่อฐานข้อมูลไม่ตรง ตรวจ POSTGRES_USER และ POSTGRES_DB ในไฟล์ .env
ไม่มีไฟล์ใหม่มาหลายวัน cron อาจไม่ทำงาน ตรวจด้วย sudo crontab -l ว่ามีบรรทัดอยู่จริง และดู /var/log/autoslip-backup.log
พื้นที่ดิสก์ใกล้เต็ม ลดจำนวนวันที่เก็บ เช่น KEEP_DAYS=7 ./scripts/backup.sh หรือแก้ค่าเริ่มต้นในสคริปต์

หัวข้อ 7ข้อจำกัดที่ควรรู้

จุดอ่อนที่เหลืออยู่

ไฟล์สำรองอยู่บนเครื่องเดียวกับฐานข้อมูล

ระบบนี้กันได้กรณี ลบข้อมูลผิด หรือ อยากย้อนกลับไปวันก่อน แต่ ไม่ช่วยถ้าเซิร์ฟเวอร์พังทั้งเครื่อง เพราะไฟล์สำรองจะหายไปด้วย

ถ้าต้องการกันจุดนี้ด้วย มีสองทาง — เปิด snapshot อัตโนมัติของ DigitalOcean (ประมาณ $1.20 ต่อเดือน สำรองทั้งเครื่อง) หรือเพิ่มการก๊อปไฟล์สำรองออกไปเก็บที่อื่นทุกวัน

สิ่งที่ไฟล์สำรองไม่ได้เก็บ

  • ไฟล์ตั้งค่า .env และ credentials.json — เก็บสำเนาไว้ที่ปลอดภัยแยกต่างหาก
  • ข้อมูลใน Google Sheets — อยู่บน Google อยู่แล้ว มีประวัติย้อนหลังของตัวเอง
  • รูปสลิป — ระบบไม่ได้เก็บรูปไว้ ลบทิ้งทันทีหลังอ่าน QR เสร็จ

ความปลอดภัยของไฟล์สำรอง

ไฟล์สำรองมีข้อมูลธุรกรรมทั้งหมด จึงตั้งสิทธิ์ให้อ่านได้เฉพาะ root และเก็บไว้นอกโฟลเดอร์โปรเจกต์ — อย่าคัดลอกไปวางในที่ที่คนอื่นเข้าถึงได้ และอย่าเอาขึ้น GitHub
